## היקף הבדיקה והבחנה בין הגרסאות

נבדקו מסכי React, שירותי הלקוח, נתיבי Express, שירותי הדומיין, סכמת Prisma, המיגרציות וקובצי הבדיקות. בסיס ההשוואה הוא `HEAD=b2bb47f`. בסביבת העבודה כבר קיימים שינויים לא־מחויבים רבים, ובהם מודול `journey`, תהליכי קליטה שמורים ומסכים חדשים. לכן:

- **בסיס Git** להלן הוא ההתנהגות בקוד השמור, לפני השינויים הלא־מחויבים.
- **העבודה הקיימת** היא הקוד שנמצא כעת בדיסק. זהו מימוש חלקי שיש לבדוק ולהשלים, ולא הוכחה שהדרישה הושלמה.
- בסבב הבדיקה הזה לא שונו קוד יישום, סכמת DB או נתונים. נוסף רק מסמך זה. השינויים הקודמים לא בוטלו.
- זו בדיקה סטטית של הקוד. לא בוצעו בסבב זה בדיקות משתמשים, ריצת דפדפן או אימות מול דוחות פיננסיים אמיתיים. קיום קובץ בדיקה אינו מעיד שהיא עברה. מצב החלת המיגרציה על כל סביבה דורש בדיקה לפני המימוש הבא.

במפות הקבצים: `F/` פירושו `frontend/src/`; `B/` פירושו `backend/src/`. נתיבים המסומנים **מוצע** עדיין אינם קיימים; נתיבים המסומנים **עבודה קיימת** קיימים בדיסק אך אינם ב־HEAD.

## מסקנת המוצר

התשתית העיקרית כבר קיימת. הבעיה המרכזית היא שהמשתמשת נדרשת להבין את מבנה המערכת כדי להגיע לתמונה פיננסית אמינה: בחירת מסך ייבוא, מעבר לאישור אשראי או להתאמות בנק, והבחנה עצמאית בין עודף חודשי, יתרת חשבון והתחייבויות.

הכיוון המומלץ: **איפה אנחנו עומדים → מה צפוי → מה כדאי לעשות עכשיו**. הייחוד צריך להיות מסלול קצר ומובן שמחבר את המספר למקור שלו ולפעולה המתאימה. אין צורך להוסיף עוד ציון, גרף או מנגנון AI כדי להשיג זאת.

שלושת החסמים הראשונים הם:

1. המספר „מותר להוציא היום” בבסיס Git אינו מחושב מכסף זמין לאחר התחייבויות.
2. ההיכרות מסומנת כהושלמה לפני שהמשתמשת סיימה להעלות ולבדוק מידע.
3. תהליכי קליטה שונים שומרים נתונים ומדווחים על הצלחה בשלבים שונים, ללא הגדרה אחידה של „הושלם”.

## 1. „מותר להוציא היום” — החישוב, המקורות והתיקון

### ההתנהגות המדויקת בבסיס Git

`B/modules/dashboard/insights.service.ts`, הפונקציה `buildInsights`, קוראת ל־`totals` ול־`dashboardRepository`:

```text
I = סכום Income.amount לפי incomeDate בחודש הנבחר
E = סכום Expense.amount לפי expenseDate בחודש הנבחר
  + סכום CreditTransaction.amount לפי billingDate באותו חודש,
    רק כאשר CreditImport.status = confirmed
    ורק כאשר transactionType != financing
B = round2(I - E)
L = מספר הימים בחודש פחות היום בחודש, ללא היום הנוכחי

אם I=0 וגם E=0: safePerDay = null
אחרת, אם החודש אינו הנוכחי: safePerDay = null
אחרת, אם L>0 וגם B>0: safePerDay = floor(B/L)
אחרת: safePerDay = 0
```

הסכומים הם של כל החודש, ולא בהכרח עד היום. רשומה עתידית באותו חודש יכולה להיכלל. זיהוי החודש והיום נעשה לפי אזור הזמן של תהליך השרת. ביום האחרון בחודש מתקבל אפס גם אם נשאר עודף. הכותרת אומרת „היום”, אך המכנה אינו כולל את היום.

**כל מקומות השימוש שנמצאו:** תצוגה פעילה אחת בבסיס Git, ב־`F/pages/DashboardPage.tsx`, כרטיס `SummaryCard` סביב שורה 180 ב־HEAD. התוצאה עוברת דרך `B/modules/dashboard/dashboard.controller.ts`, `dashboard.routes.ts`, `F/services/dashboard.service.ts`, והטיפוס `DashboardInsights` ב־`F/types/models.ts`. `InsightsPanel.tsx` מזכיר safe-to-spend בהערה, אך אינו מציג את השדה. `dailyToStayOnTrack` באותו שירות הוא מדד אחר — תקציב יומי לעמידה ביעד — ואסור להפוך אותו לתחליף ליתרה זמינה.

**העבודה הקיימת:** `safePerDay` הוחלף ב־`null`, הבית משתמש ב־`getFinancialStatus`, ונוסף חישוב ב־`journey/allowance.ts`. זו התחלה בכיוון הנכון; עדיין קיימים פערי התאמה וכיסוי המתוארים בהמשך.

### ההתנהגות המוצעת והנוסחה

השם המומלץ לתצוגה: **„אומדן להוצאה יומית לאחר התחייבויות”**, עם אופק עד סוף החודש. אם רוצים להשאיר כותרת שיווקית קצרה, ההסבר והמגבלות חייבים להישאר ליד המספר. זהו אומדן תכנון המבוסס על המקורות הרשומים, לא הרשאה להוציא כסף.

תחילה בונים רשימת אירועי מזומן מנורמלת. לכל אירוע: מקור ומזהה יציבים, תאריך, סכום או `null`, חשבון משלם כשידוע, רמת ודאות, מצב תשלום וקישורי התאמה. חיוב אשראי מרוכז נספר פעם אחת; המנוי שבתוכו אינו מנוכה שוב. תשלום שכבר ירד ונכלל בעוגן הבנק אינו מנוכה שוב.

נסמן:

- `t` — היום העסקי בישראל; `H` — סוף החודש; `N` — מספר הימים מ־t עד H, **כולל היום**.
- `C` — מזומן זמין מאומת לתאריך t בחשבון/מאגר המימון הרלוונטי. לא כוללים מסגרת אשראי, הכנסה צפויה או יתרות חיסכון שכבר כלולות בו.
- `R` — כרית ביטחון וכסף ששוריין במפורש, כולל חוב אשראי שכבר נוצר אך משולם אחרי H, ככל שאינו נכלל בתזרים בתוך האופק. כל רכיב משוריין פעם אחת.
- `O(d)` — סכום מצטבר של התחייבויות שלא שולמו, שתאריך פירעונן עד יום d. חוב עבר פתוח נדרש כבר ביום t.
- `E(d)` — יתרת הוצאות חיוניות צפויה עד d, שאינה כבר כלולה ב־O. אם המשתמשת אישרה רזרבה כוללת `E`, ברירת המחדל המוצהרת היא פריסה שווה: `E(d)=E×n(d)/N`.
- `n(d)` — מספר הימים מ־t עד d, כולל שניהם.

```text
A(d) = C - R - O(d) - E(d)
D = max(0, floor_to_agora(min over d∈[t,H] of A(d)/n(d)))
shortfall = max(0, -min over d∈[t,H] of A(d))
```

החישוב יתבצע באגורות או Decimal עם כלל עיגול מוגדר. בדיקת כל יום מונעת הצגת סכום המותיר גירעון ביום חיוב מוקדם. `shortfall` מוצג בנפרד; אפס אינו מסר „הכול בסדר”.

דוגמת קבלה: יתרה 10,000 ₪, כרית 1,000 ₪, חיובים לא משולמים 3,000 ₪, הוצאות חיוניות 1,000 ₪ ו־10 ימים כולל היום — אם אין צוואר בקבוק מוקדם, מתקבלים 500 ₪ ליום. בדוגמה נפרדת, עם אותה יתרה וכרית, ללא רזרבת הוצאות חיוניות ועם חיוב של 9,500 ₪ היום, מתקבלים אפס ו־500 ₪ פער, גם אם רשומה הכנסה צפויה למחר.

**הנחות ומידע חסר:**

1. הכנסה עתידית לא מגדילה את הסכום בגרסה הראשונה. אפשר להראות אותה בנפרד כצפויה.
2. ללא יתרה מהימנה, עם מקור נדרש חסר, עם סכום/מועד חיוב מהותי לא ידועים או עם התאמה שיכולה לשנות את התוצאה — `amount=null`, סיבה ופעולת השלמה. לא אפס.
3. אפשר להציג סכומים ידועים חלקיים, אך לא לכנותם סך ההתחייבויות המלא.
4. אין להסיק שכל המידע קיים משום שאין פריטי review, משום שיש רשומות בחודש או משום שקיים מסמך אחרון. נדרשים כיסוי לפי מקור ואישור מודע של החוסרים.
5. בעדכון ידני של יתרה היום יש להסביר שהיתרה כוללת את מה שכבר שולם עד העדכון. רישום הוצאה נוספת צריך לעדכן/לפסול את ההנחה לפי אמצעי התשלום והאם העסקה כבר נכללה; אין לנכות אותה אוטומטית גם כהוצאה וגם כתנועת בנק.
6. בכמה חשבונות, אין להניח שכסף בחשבון א' זמין לחיוב בחשבון ב'. עד להוספת שיוך מימון, אפשר להציג תמונה מאוחדת אך לא אומדן יומי מאוחד.
7. חיוב `financing` מוחרג מסיכום הוצאות צריכה, אך הדבר אינו מוכיח שאין חובת תשלום מזומן. החוב ותשלומו צריכים להופיע פעם אחת דרך מקור ההלוואה/המימון המתאים; אם לא ניתן לקבוע זאת, האומדן נשאר חסר.
8. החזרים וזיכויים צפויים אינם מזומן חדש עד שהם משתקפים ביתרה או בחשבון כרטיס מאומת. אין לקזז זיכוי בכרטיס אחד מחיוב בכרטיס אחר ללא בסיס.
9. תזכורת לא־כספית אינה חוסמת. תזכורת כספית בסכום לא ידוע כן דורשת פתרון; יש לשמור את ההבחנה.
10. השלמת ההיכרות ואפשרות להצגת אומדן יומי הן שני מצבים נפרדים. שימוש ידני חלקי יכול להיות תקין לאחר שהמגבלות הובהרו.

### גישת המימוש, קבצים ושינויים

- לשמר את `dashboardRepository` כמקור לסיכומי הכנסות/הוצאות; לא להפוך אותם לחישוב מזומן ולא להעתיק עסקאות אשראי לטבלת הוצאות.
- להשלים את `B/modules/journey/commitments.service.ts`, `coverage.service.ts`, `allowance.ts`, `journey.utils.ts`, `journey.routes.ts` הקיימים בעבודה. להפריד התאמת מקורות, כיסוי וחישוב טהור.
- להרחיב `B/modules/dashboard/cashflow.service.ts` כך שאירועי התחייבויות ישמרו מזהים, מקורות וסכומים לא ידועים. לשתף את מנוע המופעים עם לוח השנה והתחזית, בלי לכתוב חישוב שני.
- לעדכן `B/modules/bank/accountBalance.service.ts`, `bank.validation.ts`, `bank.service.ts`, `creditCoverage.service.ts`, `reconciliation.service.ts`; להוסיף אימות מחדש כשמקור תשלום משתנה או נמחק.

- בצד הלקוח: `F/pages/DashboardPage.tsx`, `AccountsPage.tsx`, `CommitmentsPage.tsx`, `F/components/common/CoveragePanel.tsx`, `MetricExplanation.tsx`, `F/services/journey.service.ts`, `F/types/models.ts` ו־`F/types/dashboard.types.ts`.

## 3. היכרות → העלאה → עיבוד → פתרון → בדיקה → תמונה פיננסית

### התהליך הקיים בבסיס Git

**Onboarding:** `F/pages/OnboardingPage.tsx` כולל שלוש פעולות: יעד חודשי, ייבוא אשראי, הוספה מהירה, וכן דילוג. כולן מפעילות `finish(to)`. הפונקציה כותבת `localStorage.mj_onboarded=1`, מנסה לשמור `notificationsJson.onboardingCompleted=true` דרך `completeOnboarding`, ומתעלמת מכשל שמירה לפני ניווט.

`RequireOnboarding` מקבל גם את דגל הדפדפן, גם את דגל ההגדרות וגם סכומים חיוביים בחודש הנוכחי כראיה להשלמה. במקרה של כשל בטעינה הוא מאפשר כניסה. הדגל המקומי אינו ממוסגר לפי userId. מכאן שהשלמה אינה מעידה על העלאה, אישור או בדיקה, ויכולה להיות מושפעת מחשבון אחר באותו דפדפן.

**Smart upload:** `ImportsPage.onSmartFile` ו־`DocumentsPage` שומרים `lastFile` ותגובות בזיכרון React, שולחים שוב את הקובץ עם תשובות ל־`POST /api/imports/smart`. אין session שמור בבסיס. טעינת דף מחדש מאבדת את השיחה המקומית. זיהוי בנק/אשראי משתמש בכותרות; unknown שואל סוג. בחשבון בנק יחיד נעשה שיוך אוטומטי, בכמה חשבונות נשאלת שאלה, וללא חשבון מתקבלת שגיאה שמפנה ליצירת חשבון במסך אחר. לוח סילוקין מזוהה אך מופנה להעלאה נוספת בהלוואות. PDF מזוהה כבנק לפי הפורמט, ולא לפי תוכנו.

**Spreadsheet:** `importsService.importExpenses` קורא `parseExpensesFile`, מתאים קטגוריה ואמצעי תשלום, שומר כל שורה בתאריך שלה או ביום הראשון בחודש שנבחר. הנתונים נעשים הוצאות מיד; אין שלב אישור משותף. מניעת כפילות כבר משתמשת במספר מופעים של שם+סכום+תאריך, כך ששתי רכישות זהות בקובץ נשמרות כשאין מופעים קיימים.

**אשראי:** `creditService.createImport` יוצר `CreditImport.pending` ועסקאות. `CreditPage` מאפשר לפתוח דוח, לראות שורות וסכומים, לסנן, לשנות קטגוריה ולשייך כרטיס; `confirmImport` מאשר ומריץ שוב התאמות בנק. רק confirmed נכנס לסיכומי ההוצאות. עדכון שורה ב־API הקיים מוגבל לקטגוריה; אין עריכת סכום/תאריך מלאה בתוך review.

**בנק:** `bankService.importStatement` מפרסר, שומר דוח מקור ותנועות, מחשב יתרה ומפעיל התאמות. דוח כבר יכול להשפיע על התמונה לפני שהמשתמשת עברה למסך review. `BankReconcilePage` כולל סיכומים, רשימת `needsReview`, הכנסות, הוצאות, חיובי אשראי, הלוואות ופעולות התאמה/החרגה/איפוס. בבסיס Git, אפילו `getReconciliation` מפעיל `resolveAll`; בעבודה הקיימת הוסרה תופעת הלוואי הזו.

**כפילויות:** אשראי מזהה קובץ זהה לפי SHA-256 וגם דמיון שורות; בנק לפי חשבון+תאריך+סכום+סוג+תיאור. בבסיס Git, שימוש ב־Set בבנק ובאשראי עלול להסיר שתי תנועות אמיתיות זהות בתוך קובץ. בעבודה הקיימת נעשה מעבר לספירת מופעים. התאמה חלשה בין קבצים עדיין אינה הוכחה לכפילות — אין תור החלטות שמציג את זוג הרשומות לפני דילוג.

**מסמכים:** `documentsService.record` שומר מטא־נתונים וקובץ כמיטב יכולתו; כשל אינו מכשיל את הייבוא. קיימים צפייה במקור ו־rollback לבנק/אשראי בלבד. מחיקת רישום מסמך שונה מביטול קליטה. הייבוא הישיר של גיליון הוצאות אינו מספק אותו lineage כמו דף בנק.

### המסע המוצע

```text
היכרות: אילו מקורות יש ומה נרצה להבין?
→ העלאה אחת
→ שמירת קובץ ויצירת session
→ זיהוי ועיבוד
→ השלמת מקור/תאריכים/שורות לא ברורות/כפילויות חשודות
→ תצוגת השינויים וההשפעה הצפויה
→ אישור והחלה אטומית
→ review של תוצאות והתאמות נדרשות
→ סיכום: מה כלול, עד מתי, ומה עדיין חסר
→ השלמת ההיכרות, רק אם דרישות המסלול הושלמו
```

המערכת שומרת כל שלב. חזרה ממסך אשראי או התאמות מחזירה לאותו session ולא לתחילת המסע. אפשר „להמשיך אחר כך” בלי לסמן completed. אין לכפות יעד חודשי או כרטיס אשראי למי שאין לה כאלה.

**כלל השלמת onboarding בצד השרת:** הוגדרו מקורות רלוונטיים; לפחות מסלול נתונים ראשון נבחר והושלם — קליטה מאושרת או הזנה ידנית שנבדקה, כולל הצהרת אין־פעילות מפורשת כשזה המצב; אין סוגיות חוסמות במסלול הראשון; המשתמשת ראתה את סיכום הכיסוי והמגבלות ואישרה אותו. לא מסיימים עקב ניווט, כפתור skip, היעדר שגיאה או יתרה חיובית. פריטים בלתי רלוונטיים/מבוטלים לא צריכים לכלוא את המשתמשת ב־onboarding.

השלמת onboarding לא מתירה אוטומטית אומדן יומי. לדוגמה, מסלול הוצאות ידניות ללא בנק יכול להסתיים עם תמונת הוצאות ברורה ועם „אין מידע מספיק ליתרה זמינה”. משתמשים ותיקים יקבלו מצב `legacy`, ולא חותמת כיסוי מאומתת בדיעבד.

**מצבי session:** `uploaded → processing → needs_input/ready_for_review → committing → review → completed`; מסלולי צד `failed`, `cancelled`, `rolled_back`. בעבודה הקיימת יש חלק ממצבים אלה; `processing` וכשל עיבוד אינם נשמרים כמסלול מלא. נדרשת רשימת מעברים חוקיים ולא מחרוזת חופשית בלבד.

### מימוש מדויק ושימוש חוזר

1. להשתמש ב־`ImportSession` שבעבודה וב־`importSession.service.ts`; לשמור session לפני parse כך שגם כשל פתיחה ניתן לשחזור. לשמור parserVersion, hash, תשובות וגרסה.
2. להפיק רשומות preview עם `rowId`, טווח/שורת מקור, original/normalized values, warnings, duplicate candidates ו־resolution. להוסיף `ImportRow` **מוצע** אם נדרשת עריכת שורות ואינדוקס; לא להשאיר טבלת preview שלמה בתוך JSON כשצריך עימוד ועריכה.
3. להשתמש בפרסרים הקיימים — `parseBankStatement`, `parseBankStatementPdf`, `parseCreditFile`, `parseExpensesFile`, `parseLoanSchedule` — ללא שכפול לוגיקת סכומים.
4. להוסיף adapters ל־prepare/validate/commit של כל סוג. הפרדת validation מכתיבה צריכה לאפשר הצגת דחיות לפני יצירת כסף.
5. קובץ זהה מפנה לייבוא הקיים; חפיפה ודאית מדלגת עם פירוט; דמיון לא ודאי מוצג לפתרון. לשמור כמה מופעים זהים אמיתיים, ולהבחין בין רכישה ידנית לבין רכישה מיובאת במקום לסמוך רק על שם וסכום.
6. להחיל באותה טרנזקציה את שורות הדומיין, מקור הייבוא ותוצאת session. תשובה חוזרת אחרי timeout חייבת להחזיר אותה תוצאה. עדכון בגרסה ישנה יחזיר 409.
7. לשמור קישור מפורש לכל שורה שנוצרה/עודכנה/דולגה. לא להסיק IDs מהפרש בין „כל ההוצאות לפני” ו„כל ההוצאות אחרי” — כתיבה ידנית מקבילה יכולה להשתחל.
8. לחבר את `CreditPage` ואת רכיבי ההתאמות הקיימים ל־review אחיד, עם קישור מדויק ל־import/row ומסלול חזרה. לשמר טיפול רק בפריטים המחייבים תשומת לב, עם אפשרות להציג הכול.

## 5. בדיקת כסף שבועית — Update → Resolve → Understand → Act

**מצב בבסיס:** אין flow שבועי שמור או snapshot קודמת. קיימים כל אבני הבניין: קליטה, התאמות, תשומת לב, מועדי התחייבויות, יעדים ותקציבים.

**העבודה הקיימת:** `CheckInPage`, `MoneyCheckIn` ו־`checkin.service.ts` מוסיפים draft, ארבעה שלבים, השוואת snapshots וסיום. ההשוואה מבחינה בהוספה, שינוי, מחיקה וקליטת מידע היסטורי. זה בסיס טוב לשימוש חוזר, אך כרגע קורא ושומר את כל ההיסטוריה בכל תמונה והפעולה הבאה נבחרת מ־issue ראשון או יעד ראשון.

| שלב | התנהגות מוצעת | שימוש חוזר ותלות |
|---|---|---|
| Update | להראות לכל מקור עד מתי הוא מכוסה והאם נדרש עדכון; „אין מידע חדש” אפשרי עם הצהרה שתישמר; להמשיך session קודם | `financialStatus`, מסמכים, coverage, `/imports` |
| Resolve | להציג רק חסימות ואזהרות רלוונטיות; פעולה בתוך המסע או קישור מדויק עם חזרה; לא לעבור על כל תנועה תקינה | `review`, התאמות בנק, אישור אשראי, קטגוריות |
| Understand | עד שלושה שינויים משמעותיים, מצב הכיסוי, חיובים בשבוע הקרוב ופיגורים; מידע ישן שנקלט היום מוצג בנפרד מהוצאה חדשה השבוע | `compareSnapshots`, סיכומי דומיין ו־commitments |
| Act | פעולה אחת עם סיבה: להשלים מקור שחוסם תמונה, להסדיר פער חיוב קרוב, או להתקדם ליעד רלוונטי; אפשר לשמור כצעד הבא | דירוג פעולות משותף לבית, יעדים, תקציבים |

הבדיקה אינה דורשת שבעה ימים בדיוק כדי להיפתח. לאחר שבעה ימים מאז הבדיקה המושלמת האחרונה תופיע הזמנה רגועה. יציאה באמצע שומרת draft. קישור לפעולה אינו הוכחה שהפעולה בוצעה. בדיקה יכולה להסתיים עם מגבלות מידע מוצהרות כאשר אין תנועות בלתי פתורות שמשנות את המשמעות הכספית; snapshot חלקית מסומנת כך ואינה מייצרת מסקנות מזומן מלאות.

**מימוש:** לשמור timestamps, source coverage, calculationVersion, גרסת נתונים ופעולה נבחרת בעת complete. להשוות מול snapshot בלתי משתנה של ההשלמה הקודמת, ולא מול חישוב מחדש שלה. לפצל שינוי כלכלי משינוי בידע; שינוי סכום/מחיקה אינם הוצאה חדשה. להחליף בהדרגה snapshot של כל השורות בסיכומים ו־revision/change log מדופדף, כדי למנוע גידול בלתי מוגבל. לדרג את הפעולה באמצעות אותו מנגנון של Home ולא לפי סדר `id`.

**קבצים לשינוי:** `F/pages/CheckInPage.tsx`, `DashboardPage.tsx`, `ReviewPage.tsx`, `ImportJourneyPage.tsx`, `F/services/journey.service.ts`, `F/app/App.tsx`, `navigation.ts`; `B/modules/journey/checkin.service.ts`, `review.service.ts`, `coverage.service.ts`, `journey.routes.ts`, `B/modules/dashboard/attention.service.ts`, `backend/prisma/schema.prisma` ומיגרציה.

**DB/API:** כן. `MoneyCheckIn` כבר קיים בעבודה. להוסיף סכמת snapshot עם version, בחירת פעולה מפורשת ומצב coverage; למנוע שני drafts פעילים למשתמש גם בבקשות מקבילות. להשתמש ב־`GET/POST /api/journey/check-in`, `PATCH /:id`, `POST /:id/complete`; complete יבדוק גרסה ותנאים בשרת.

**סיכונים ובדיקות:** השוואה הראשונה אינה „שיפור של 100%”; נתוני שבוע חסר אינם אפס; קליטה מאוחרת נפרדת; snapshot ישנה אינה משתנה; רענון/חזרה/שני מכשירים; סיום כפול idempotent; פעולה אינה מסומנת אוטומטית כמבוצעת; אין השוואת מזומן מלאה כאשר הכיסוי חלקי. להרחיב `journey.integration.test.ts` ולהוסיף `journey/checkin.service.test.ts` **מוצע** ולבדוק flow מלא ב־E2E.

## 7. תיקון מיידי אחרי Quick Add

**מצב בבסיס:** `parseQuickAdd` הוא פרסר דטרמיניסטי בעברית, ללא LLM. מזהה מספר ליד מטבע או את המספר הגדול בטקסט, מסיר מילים, מזהה היום/אתמול/שלשום ומשתמש בקטגוריזציה הקיימת. `quickAddService.add` שומר מיד Expense ומחזיר את הרשומה ואת הפירוש. `QuickAddBar` מציג סכום, בית עסק וקטגוריה בלבד. אין Undo/Edit, ותאריך והערת הרשומה אינם מוצגים. הקלדה חדשה מעלימה את אישור השמירה.

**בעיות:** מספרים נוספים בתיאור עלולים להתפרש כסכום; פסיק אלפים בבסיס מתפרש כשבר עשרוני; הסרת תחיליות יכולה לשנות שם בית עסק; תאריך יחסי נשען על שעון השרת. אלה סיבות להציג את הפירוש, לא להסתירו מאחורי „נשמר”.

**מוצע:** אחרי שמירה מוצג אישור יציב: סכום, קטגוריה/ללא קטגוריה, בית עסק, תיאור ותאריך, עם „עריכה” ו„ביטול ההוספה”. העריכה פותחת את אותו טופס הוצאה קיים. Undo מוחק רק את `expense.id` שהוחזר; ללא חיפוש לפי שם/סכום. השהיית השרת או כשל מחיקה משאירים את האישור ואת האפשרות לנסות שוב. לא סוגרים אותו אוטומטית אחרי שניות ספורות. הוספה חדשה אינה שוללת גישה לרשומה הקודמת; לכל הפחות קישור קבוע ל„ההוצאה שנוספה”.

**העבודה הקיימת:** נוסף `ExpenseEditor` משותף ו־Undo/Edit; הפרסר טופל לפסיק אלפים ולתאריך ישראלי. יש לבדוק את כללי ambiguity ואת שינויי הבית אחרי ביטול/עריכה. אין צורך לבנות שירות עריכה חדש.

**קבצים ופונקציות:** `F/components/common/QuickAddBar.tsx`, `F/components/expenses/ExpenseEditor.tsx`, `F/pages/ExpensesPage.tsx`, `F/services/finance.service.ts` (`quickAddExpense`, `updateExpense`, `deleteExpense`), `F/hooks/useAsync.ts`, `F/services/api.ts`; `B/modules/expenses/quickAdd.service.ts`, `expenses.routes.ts`, `expenses.controller.ts`, `expenses.service.ts`, `expenses.repository.ts`, `expenses.validation.ts`.

**DB/API:** Undo/Edit הבסיסיים משתמשים ב־PATCH/DELETE הקיימים ואין צורך במיגרציה. כדי למנוע הוצאה כפולה אחרי retry של POST שנשמר אך תשובתו אבדה, להוסיף idempotency key ליצירת הוצאה ולשמור תוצאה/מפתח ייחודי — הרחבת API ו־DB נפרדת אם תומכים בניסיון חוזר אוטומטי. מנגנון רענון צריך לפסול גם אומדן/כיסוי רלוונטיים.

**סיכונים ובדיקות:** ביטול מוצלח/כושל, עריכה שמשנה חודש, double click/retry, מחיקה שכבר בוצעה, חשבון אחר, „אתמול” סביב חצות, „1,250”, שני מספרים, שם עסק עם מספר, ללא קטגוריה. להוסיף `B/modules/expenses/quickAdd.service.test.ts` **מוצע**, בדיקת API מדויקת ועדכון E2E. להראות את ערכי הרשומה שנשמרה ולא רק את `parsed` שאולי כבר אינו תואם לאחר עריכה.

## השפעה ארכיטקטונית וחוזים משותפים

אין הצדקה לפיצול לשירותים נפרדים. להוסיף שכבת תזמור בתוך השרת הקיים, מעל שירותי הדומיין:

```text
מסכי Home / Onboarding / Import / Review / Weekly Check-in
                         ↓
             journey API + import session API
                         ↓
        כיסוי מקורות / התחייבויות / תור טיפול / פעולות
                         ↓
     שירותי bank / credit / loans / expenses הקיימים
                         ↓
             Prisma + מסמכי מקור שמורים
```

### חוזי המידע

| חוזה | שדות/אחריות | בעלות |
|---|---|---|
| `FinancialStatus` | תאריך נוכחי, כיסוי, חסמים, מדדים וגרסה עקבית | journey/coverage |
| `Commitment` | מקור, מזהה מופע, סכום nullable, dueDate, account/card, ודאות, מצב תשלום/התאמה | journey/commitments ושירותי הדומיין |
| `ReviewItem` | מזהה יציב, קוד בעיה, חומרה, מה מושפע, פתרון, sourceRef ו־returnTo | journey/review |
| `ImportSession` | קובץ, סוג, parserVersion, גרסה, מצב, שורות/החלטות, תוצאות וקשרים | imports/session |
| `FinancialMetric` | מספר והסבר מאותה גרסת נתונים | שירות המדד + טיפוס משותף |
| `MoneyCheckIn` | draft/השלמה, snapshot בלתי משתנה, מגבלות ופעולה | journey/checkin |

יש להוציא טיפוסים פיננסיים מהצהרות מקומיות בקומפוננטות/קובצי שירות אל קובצי הטיפוסים. ה־UI מציג; הוא אינו משכפל נוסחה או מנגנון מניעת כפילות.

### DB ומיגרציות

בעבודה הקיימת נוספו `ImportSession`, `FinancialProfile`, `CommitmentDecision`, `MoneyCheckIn` והמיגרציה `backend/prisma/migrations/20260917100000_money_journey/migration.sql`. זו אינה תשתית שלמה לכל הדרישות:

- להוסיף כיסוי לפי מקור: סוג/מזהה, טווח מדווח לעומת טווח תנועות, מועד אימות, חוסרים ו־revision. אישור שלושה checkbox-ים אינו תחליף לכיסוי לפי חשבון/כרטיס.
- לקבוע versioning של מצב פיננסי. כל כתיבה כספית רלוונטית, כולל Quick Add, edit/delete, אישור אשראי, rollback ושינוי יתרה/התחייבות, משנה revision. בדיקת גרסה והשלמה צריכות להיות אטומיות מול אותן כתיבות.
- החלטות התחייבות צריכות קשר למקור, סכום מותאם, החלטה קודמת/חדשה ו־updatedAt. נדרש למנוע כיסוי כולל העולה על סכום תשלום, לא רק לבדוק כל שורה בנפרד.
- לשמור התחייבויות עבר פתוחות עד פתרון, ולא להעלימן בעקבות חלון תצוגה מתגלגל.
- להוסיף `ImportRow`/lineage אם משיקים עריכה ופתרון כפילויות בשורה. קישור חשבון/כרטיס משלם נדרש לתכנון מכמה חשבונות.
- לשמור snapshot עם schema/calculation version ומדיניות גודל. אין צורך לשכפל ledger שלם לכל שבוע.

לפני כל מיגרציה נוספת: לבדוק מה כבר הוחל בכל סביבה ולהשוות schema. אם המיגרציה הקיימת הוחלה, אין לערוך אותה בדיעבד; מוסיפים מיגרציה קדימה. `legacy` משמר כניסה למשתמשים ותיקים, אך אינו מצהיר שהנתונים שלהם מאומתים.

### טרנזקציות ורענון

`B/config/database.ts` שבעבודה שונה ל־Prisma Proxy ו־AsyncLocalStorage עם נעילת שורת משתמש. זו השפעה רוחבית על כל השרת, לא פרט של מסך קליטה. יש לבדוק nested transactions, שימוש callback לעומת array, rollback וכשל באמצע. עדיף גבול Unit of Work מפורש עם client המועבר לשירותים המתאימים אם ניתן לעשות זאת בלי לשכתב את הפרויקט. אין להסתפק בנעילת session כאשר נתיבי כתיבה אחרים ממשיכים לשנות את אותם נתונים ללא אותו מנגנון.

`F/services/api.ts` ו־`F/hooks/useAsync.ts` שבעבודה מרעננים באמצעות אירוע גלובלי לכל mutation. יש לצמצם לפי דומיין/query ולהימנע מסערת בקשות, שמירת מספר ישן לאחר mutation, או איפוס טפסים. כשל עדכון אינו completion; כשל fetch אינו אפס.

קבצים שמורים נדרשים לתהליך resume. מחיקת Document לא יכולה למחוק bytes שעדיין נדרשים ל־session או למסמך אחר באותו path. להשתמש בבעלות/ספירת references ובהסרת קבצים שאינם בשימוש, במקום למחוק אוטומטית path משותף.

| קובץ session יכול להימחק עם Document | `documentStorage.save` מחזיר path דטרמיניסטי ו־documents.remove מוחק אותו | הגנה על references ושמירת provenance חובה |
| complete חוזר תלוי עדיין בקובץ | `commit` קורא bytes לפני שבודק אם session כבר completed/review | להחזיר תוצאה שמורה תחילה; אימות עקבי של הבקשה |
| תור פעולות אינו אחיד | Home מנכה לפי URL; check-in בוחר issue/goal ראשון | דירוג סמנטי משותף |
| קישור review אינו ממוקד בפועל | `review.service` מוסיף `row`; `BankReconcilePage` אינו קורא אותו | deep link, פתיחה/הדגשה וחזרה למסע |
| מסלולי API ישנים עוקפים staging | POST ישירים ב־imports/credit/bank/loans נשארו | מתאם תואם לאותו orchestrator |
| דרישת אימות ידני לכל אירוע עלולה להכביד מאוד | כל event בלי decision חוסם allowance | התאמה אוטומטית כשמוכחת; להראות למשתמשת רק מקרים לא ודאיים |
| שינויים רוחביים מגדילים את סיכון השחרור | Prisma Proxy, רענון גלובלי, שינויי פרסרים וניווט באותה חבילה | לפצל ליחידות ביקורת קטנות ובדיקות ממוקדות |

בנוסף קיימים שינויים קודמים בקובצי אימות/בדיקות שאינם חלק ישיר מעיצוב המסע. אין לכלול אותם אוטומטית באותו commit או לדרוס אותם במהלך פיצול העבודה.

## תוכנית מימוש בשלבים וסדר תלות

### Phase 1 — Critical correctness issues

**תכולה:** להסיר את ההבטחה בחישוב הישן; להפריד עודף חודשי ממזומן וחיסכון רשום מנכס נוסף; לאחד כללי תאריכים; לתקן מניעת כפילויות בלי למחוק תנועות זהות אמיתיות; להגדיר commitment/coverage/metric contracts; להשלים תוקף התאמות, פיגורים ופסילת כיסוי. להפעיל guard בצד השרת להשלמת onboarding. לפני תכנון אומדן לכמה חשבונות — להציג unavailable או להשלים שיוך מימון.

**קבצים מרכזיים:** מודולי journey, bank, credit, dashboard/insights, quickAdd, AccountsPage, schema/migrations והטיפוסים. זהו גם השלב לביקורת Prisma Proxy ולגבולות טרנזקציה.

**תנאי יציאה:** אין מספר חיובי המבוסס רק על עודף חודשי; חסרים מוצגים כלא־ידוע; חיוב נספר פעם אחת; שינוי/מחיקת מקור מבטלים התאמה ישנה; פרסרים וסיכומי הוצאות שומרים את האינווריאנטות הקיימות. לא משיקים allowance לפני תנאים אלה.

### Phase 2 — Home simplification

**תכולה:** ארבעת האזורים המוצעים, עד שלוש פעולות, כיסוי/תאריך ליד המספר, ניתוח בטעינה עצלה, מצב ריק אמיתי, שורת חודש משנית. להשתמש במצב חלקי כששלב 1 עדיין אינו מאפשר חישוב.

**קבצים מרכזיים:** DashboardPage, HomeAnalysis, AttentionPanel, UpcomingPanel, שירותי dashboard/journey, CSS וחוזה פעולות.

**תנאי יציאה:** המשתמשת רואה מצב, קרוב ופעולה ללא גלילה דרך גרפים; אין כפל נתונים; אין טעינת ניתוח לפני פתיחתו; 0–3 פעולות בלבד; שגיאות אינן מוצגות כמצב תקין.

### Phase 3 — Onboarding / Import / Review flow

**תכולה:** כניסת `/imports` אחת, session שמור, זיהוי ו־preview, פתרון שורות וכפילויות, commit אטומי, review ממוקד, lineage ו־rollback תואם, onboarding עם השלמה שרתית ומסלול ידני. לחבר את ההעלאות ההקשריות וה־APIs הישנים לאותו תהליך. להכניס את חלוקת ניהול/מידע הבסיסית כדי שלמסע יהיו יעדים יציבים.

**קבצים מרכזיים:** importSession, import adapters, Documents/storage, Onboarding/RequireOnboarding, ImportJourney/Review, Credit/BankReconcile, App/navigation והסכמה.

**תנאי יציאה:** כל פורמט נתמך עובר upload→review→complete; refresh אינו מאבד שלב; retry אינו יוצר כסף נוסף; שגיאת עיבוד ניתנת להמשך; onboarding לעולם אינו completed עקב פתיחת מסך או דילוג. קובץ מקור והנתונים שנוצרו ממנו ניתנים לאיתור.

### Phase 4 — Weekly Check-in

**תכולה:** ארבעת השלבים, draft/resume, snapshot מהשלמה קודמת, הבחנה בשינויים היסטוריים, חיובים קרובים ופעולה אחת מדורגת. לא להוסיף תשתית שליחת הודעות כדי להשיק — הזמנה בתוך האפליקציה מספיקה.

**קבצים מרכזיים:** checkin.service, MoneyCheckIn, CheckInPage, דירוג פעולות ותור review.

**תנאי יציאה:** סיום חוזר idempotent; השוואה ניתנת להסבר; אין מסקנות כוזבות ממידע חלקי; הפעולה קשורה לנתונים/יעד ולא נבחרת רק מפני שהיא הראשונה ברשימה.

### Phase 5 — Explainability and UX improvements

**תכולה:** פירוט מקורות לכל המדדים החשובים, חוזה הסבר אחיד, עימוד מקורות; גימור Quick Add Undo/Edit; Transactions עם URL filters ונתונים לפני ניתוח; חזרה עקבית מ־review; השלמת נגישות ומובייל. הסברים בסיסיים למספרים קריטיים ו־Undo הנדרשים לבטיחות כבר נכנסים בשלבים מוקדמים — שלב זה מרחיב ומאחד אותם.

**קבצים מרכזיים:** MetricExplanation, שירותי המדדים, QuickAdd/ExpenseEditor, Transactions/Expenses/Incomes, שירותי lookup/filters ו־CSS.

**תנאי יציאה:** אפשר להגיע מכל מספר חשוב למקור ולנוסחה; עריכה/ביטול מרעננים את המסכים הנכונים; מסננים שורדים refresh/back; סכומים מתיישבים עם הפירוט.

### Phase 6 — Branding and cleanup

**תכולה:** Money Jungle בכל theme; הסרת מיתוג משתנה וקוד upload/UI מת; ניקוי routes תוך שמירת redirects; השלמת ארבע קבוצות הניהול; צמצום hooks/refresh כפולים, הערות ושמות ישנים; תיעוד חוזים ומגבלות.

**קבצים מרכזיים:** brand/ThemeContext/Sidebar/Login/index.html, Manage/SettingsHub, App/navigation, wrappers ישנים ותיעוד.

**תנאי יציאה:** כל שמונה הערכות שומרות שם קבוע; אין מסך ייבוא מתחרה או קישור שבור; אין הסרת תפקוד של חשבונות/דוחות/CRM; בנייה ובדיקות שחרור תקינות.

**הסדר הפנימי המומלץ:** נכונות וחוזי מידע → API מצב/פעולות → Home → session ו־lineage → חיבור כל ההעלאות → כללי השלמת onboarding → check-in → פירוט מקורות/תנועות → branding וניקוי. תשתית חוזי session מוגדרת בשלב 1, גם אם המסכים נמסרים בשלב 3. כך שלב 2 אינו נבנה על חוזה שעומד להתחלף.

## תוכנית אימות ושחרור

בכל יחידת שינוי: בדיקה ממוקדת למקרה הפיננסי או למסלול UX שהשתנה, ורק לאחר מכן בדיקות הרגרסיה התלויות בו. לשמור בדיקות pure לחישוב, integration עם MariaDB לטרנזקציות/הרשאות, ו־E2E למסלולים בדפדפן. בדיקות E2E עם mock API אינן מוכיחות atomicity או תקינות פרסר.

פקודות קיימות לשלב המימוש:

```text
frontend: npm run build
backend:  npm run typecheck
backend:  npm run typecheck:test
backend:  npm test
backend:  npm run test:fixtures
frontend: npm run test:e2e   [נוסף בעבודה הקיימת]
```

רשימת בדיקות הרגרסיה הקיימות לשימוש: `dashboard/cashflow.service.test.ts`, `dashboard/attention.service.test.ts`, `credit/wallet.service.test.ts`, `credit/wallet.integration.test.ts`, `documents/documents.rollback.test.ts`, `loans/loanCalculator.service.test.ts`, `loans/loans.update.test.ts`, `reports/forecast.service.test.ts`, `imports/statementDetector.test.ts`, בדיקות bank parser/golden, `app.smoke.test.ts`, ו־gate/security. בעבודה קיימים גם `journey/allowance.test.ts`, `journey/journey.integration.test.ts` ו־`frontend/tests/e2e/journey.spec.ts`.

יש לוודא שקובצי fixtures אמיתיים זמינים. בדיקות שדילגו על fixture חסר אינן אימות פיננסי. אין לשנות golden כדי להפוך בדיקה לירוקה בלי התאמה למקור. לא להעתיק נתונים אישיים למסמך התכנון או ל־Git.

לפני הפעלה למשתמשים: מיגרציות בסביבה נפרדת, אימות חשבון ותיק/חדש, קובץ בנק/אשראי/גיליון/לוח אמיתי, re-import וחפיפה, rollback, משתמשים מבודדים, וסקירת מובייל/RTL בכל theme. לא להציג את העבודה הלא־מחויבת כשלמה רק מפני שקיימים routes או שהבנייה עוברת.

תוצר הביקורת הוא תוכנית זו. אין בה אישור לשחרור השינויים הקיימים; את קוד המימוש הבא יש להתחיל מ־Phase 1 ומהפערים המפורטים, לאחר החלטה על התוכנית.
